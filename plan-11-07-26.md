# Plan 11-07-26: Operational hardening + workflow UI (v1.19.0)

Execution plan for the current single-operator version. Grounded in a code audit and the
production logs/DB on kamo@192.168.0.100 (container `telegram-tc-app-1`, DB reset 2026-07-10).
Scope excludes security/auth, the SaaS build, module splitting, tsgo, and migration reorg.
Those are deferred (see end).

## Delegation protocol (who does what)

- Orchestrator: Claude Opus 4.8. Plans, sequences, reviews, runs gates, commits. Writes NO
  implementation code itself.
- Backend implementation: Codex CLI, model `gpt-5.6-luna`, reasoning effort `xhigh`.
- UI implementation (all of WS7 and any web/src change in other workstreams): Codex CLI,
  model `gpt-5.6-sol`, reasoning effort `high`.
- Review: the orchestrator (Opus) reviews every diff. Backend diffs additionally get a
  review pass from Codex `gpt-5.6-sol` at effort `high`. Findings above nit level go back
  to the implementer for a fix round (max 2 rounds, then orchestrator decides).
- Verification gate after each phase: `bun run typecheck && bun run lint && bun test`.
  Final gate additionally: `bun run build && bun run docker:build`.
- Versioning: this is backward-compatible new behaviour → minor bump to 1.19.0 in root
  package.json at the end, with a changelog.md entry. No EA protocol changes are made in
  this plan, so mt5/TelegramTC_EA.mq5 stays at its current version.
- Git: work on branch `feat/ops-hardening-1-19` off the current HEAD
  (deploy/chart-smoothing-resilience @ df4e42b5). Commit per workstream with clear
  messages. Do not push, do not touch the user's uncommitted changes in the main checkout
  (apps/api/src/app.ts WIP + apps/api/src/telegram-dead-session.test.ts).

## WS1: Held-signal queue with requeue (backend)

The core fix. Today guardian rejection marks queue items FAILED at lease time
(app.ts:2977-3001) and late opens get EXPIRED (app.ts:2331-2347); approveSignal returns
409 whenever any queue item exists (app.ts:2304-2309), so both are dead ends.

Changes:
1. Add `HELD` and `DISMISSED` to the QueueStatus union (packages/core or app.ts, wherever
   the type lives) and add columns via the existing `ensureColumn` helper:
   `queue_items.held_reason TEXT`, `queue_items.origin_queue_item_id TEXT`.
2. Guardian rejection path: instead of FAILED, set status HELD, held_reason `GUARDIAN`.
   Keep the audit event.
3. Late-open path (openTradeSourceExpired in approveSignal, and
   expireStaleOpenTradeQueueItems): instead of EXPIRED, set HELD, held_reason
   `EXPIRED_LATE`. DUPLICATE stays terminal as today.
4. NO_ACCOUNT: approveSignal currently returns 422 with no record when the provider has
   no target account. Create a HELD queue item with held_reason `NO_ACCOUNT` instead, so
   the signal is recoverable once an account is linked.
5. DELIVERY_UNKNOWN: in recoverStaleLeases (app.ts:3012-3030), a stale-leased OPEN_TRADE
   must NOT go back to PENDING (the EA posts /mt5/report once; a lost report plus
   auto-requeue can double-execute). First stale lease of an OPEN_TRADE → HELD,
   held_reason `DELIVERY_UNKNOWN`. Non-OPEN commands keep today's retry behaviour.
6. New endpoints:
   - `GET /api/queue-items/held` → held items with reason, signal summary, provider,
     account, original entry price, and the freshest EA-reported price for the symbol so
     the UI can show drift.
   - `POST /api/queue-items/:id/requeue` body `{ mode: "market" | "original" }`.
     Creates a NEW PENDING queue item copying the payload (mode market: strip/convert the
     entry so the EA executes at market with original SL/TP; mode original: keep the
     original order type and entry, including STOP orders as STOP). Sets
     origin_queue_item_id, flips the held item to DISMISSED with an audit trail. The
     one-queue-item-per-signal 409 guard in approveSignal is unchanged (requeue is a
     separate path).
   - `POST /api/queue-items/:id/dismiss` → DISMISSED.
7. Optional setting `releaseHeldOnGuardianUnpause` (default false): on manual unpause,
   guardian-held items for that account surface a one-click bulk requeue (the UI asks, WS7).
8. Guardian-held items must not be silently re-rejected: requeue while still paused
   returns 409 with a clear error.

Approval criteria:
- A guardian-paused account rejecting an OPEN_TRADE produces a HELD/GUARDIAN item;
  after unpause, requeue mode=market yields a fresh PENDING item that leases to the EA.
- A stale open produces HELD/EXPIRED_LATE and can be requeued as mode=original.
- A provider with no linked account produces HELD/NO_ACCOUNT on approve.
- A stale-leased OPEN_TRADE lands in HELD/DELIVERY_UNKNOWN and is never auto-requeued.
- Requeueing while guardian is still paused is refused.
- bun tests cover every reason path plus the double-execution guard.

## WS2: Dropped-lifecycle visibility on held items (backend)

When ingest fails to match a lifecycle command ("No open logical trade matched..."),
and a HELD OPEN_TRADE exists for the same provider (and symbol when present), link the
dropped command to that held item: new table `held_lifecycle_drops` (id, held_queue_item_id,
raw_message_id, command_type, created_at) via CREATE TABLE IF NOT EXISTS. Surface a
`droppedLifecycleCount` and the command list in `GET /api/queue-items/held`. On requeue,
include the list in the response so the UI can warn "3 lifecycle commands arrived while
held (MARK_TP_HIT, MOVE_SL, CLOSE)". Automatic replay is explicitly out of scope.

Approval criteria: a MARK_TP_HIT ingested after its open was guardian-held shows up
attached to the held item; requeue response carries the warning payload; test covers it.

## WS3: OUT_OF_SYNC resolution + close-retry guard (backend)

1. `POST /api/trades/:id/resolve` body `{ action: "close_from_history" | "readopt" | "archive" }`:
   - close_from_history: mark the logical trade CLOSED using the matching broker history
     deal(s) if found (reuse the reconciliation matchers), legs SKIPPED where no deal.
   - readopt: re-bind the logical trade to the live broker position the reconciler found
     it drifted from (only offered when the reconciler has a candidate ticket).
   - archive: terminal state, excluded from active management and out-of-sync alerts.
2. Close-retry guard: when a close/modify report comes back "No matching position found"
   (retcode 0 + that comment, as seen with GOLD#), retire the command and flip the trade
   to the reconciliation path instead of leaving it retryable. v1.18.1 fixed one such
   loop for virtual-TP; verify the plain close/modify family has the same guard, add it
   if not, with a regression test.

Approval criteria: an out-of-sync trade can be resolved via each action with correct DB
state after; a "No matching position found" report never yields a second close attempt;
tests cover both.

## WS4: Slot lifecycle (backend)

1. `DELETE /api/account-slots/:id`, allowed only for status `waiting` (never-paired).
   409 otherwise.
2. Auto-expiry: `waiting` slots older than 24h are marked `expired` lazily on
   accountSlots() read (no timer needed). Expired slots are deletable and visually
   distinct. Link-code redemption of an expired slot is refused.

Approval criteria: the two orphaned waiting slots from prod would be deletable; an
expired slot's link code no longer pairs; tests cover delete guard + expiry.

## WS5: Outbound alerting via Telegram bot (backend)

Settings additions (app_settings + PATCH /api/settings): `alertBotToken`,
`alertChatId`, and per-alert toggles. Dispatcher: on transition into an alert state,
POST to api.telegram.org sendMessage (plain fetch, 5s timeout, failures logged to audit,
never blocking the pipeline). Events, each debounced/deduped so a flapping condition
sends at most one message per 30 minutes per key:
- Equity Guardian paused (per account) and each guardian rejection.
- EA offline: no heartbeat for > 3x HeartbeatSeconds (per account, using existing
  staleness logic).
- Execution report FAILED.
- New HELD item (any reason).
- Telegram ingestion stalled (reuse existing telegram-stalled alert condition).

Approval criteria: with a mocked fetch, each event produces exactly one send with the
expected text; disabled toggles suppress; missing token disables silently; tests cover
debounce.

4. Linked Accounts: delete button (with confirm) on waiting/expired slots; "expires in
   Xh" hint on waiting slots; expired slots styled muted.
5. History/open positions: on OUT_OF_SYNC rows, a Resolve menu with the three WS3

6. QueueItem component: FAILED/HELD/DISMISSED get distinct tones; held items link to the

7. Settings: Alerting card (bot token, chat id, toggles) with a "send test message"
   button hitting a small `POST /api/admin/alert-test` endpoint (add in WS5).
8. Force-push modal pre-fill (BUG, operator-reported). Today "Correct & push" from a
   parsed signal opens a near-blank ticket forcing full re-entry, even though the parser
   already produced direction/entry/SL/TPs. Root cause: (a) `ManualSignalSeed`
   (ManualSignalModal.tsx:5-12) only carries accountId/providerId/rawMessageId/rawText/
   brokerSymbol/canonicalSymbol — NOT the parsed trade fields; (b) the seeding effect
   (ManualSignalModal.tsx:78-92) resets direction→BUY, orderType→LIMIT, entry/SL/TP/volume
   to empty; (c) ParserResult.tsx:108 calls `onClick={onForcePush}` passing the click
   event, not a seed. Fix: extend `ManualSignalSeed` with `direction`, `orderType`,
   `entry {from,to}`, `stopLoss`, `takeProfits[]`, `volume`, `executionMode`; in
   ParserResult build a full seed from `result` and pass it to `onForcePush(seed)`; in the
   modal effect pre-fill every form field from the seed when present, falling back to
   defaults only for absent fields. Net: a correctly-parsed-but-blocked or mis-parsed
   signal opens fully populated, operator tweaks at most one field. Conceptual flow to
   preserve: correctly parsed + not blocked → Approve (one click, already works);
   correctly parsed + blocked → HELD requeue (WS1); mis-parsed → Correct & push, now
   pre-filled. Add/extend a test asserting the seed pre-fills the form.
9. Tests: extend App.test.tsx / component tests for the held view actions, slot delete,
   the guardian unpause-with-requeue prompt, and the force-push pre-fill, following the
   existing test patterns.

Approval criteria: all flows drivable in the dev app against seeded data; frontend tests
green; no new global CSS files (styles/base.css cascade is order-sensitive, see repo
memory: duplicated rule blocks mean later selectors win); keyboard/focus behaviour uses
the existing ConfirmDialog/focus-trap machinery.

## Execution model: two parallel Codex streams

The bottleneck is physical, not logical: WS1-WS6 all mutate apps/api/src/app.ts, so they
cannot run as concurrent Codex tasks in one tree. But apps/web (WS7) is disjoint from
apps/api, so the UI runs fully in parallel with the backend against the API contract
pinned in this plan. Backend stays internally serial on the one file (no merge conflicts).

- Phase A (DONE): WS1 + WS4 backend → gate green → sol review → commit.
- Stream A (backend, main tree, serial on app.ts): WS2 → WS3 → WS5 → WS6 as one Codex
  task (gpt-5.6-luna xhigh). Runs after Phase A commits.
- Stream B (UI, isolated git worktree, parallel): WS7 incl. force-push modal fix
  (gpt-5.6-sol high), coded to the pinned contract below. Runs concurrently with Stream A.
- Integration: merge Stream B worktree (conflict-free, disjoint dirs) → combined gate →
  sol review of backend + Opus review of UI → reconcile any field-name drift → commit.
- Phase E: version bump 1.19.0, changelog.md entry, README additions,
  `bun run build && bun run docker:build` → final commit.

Pinned API contract (both streams MUST agree on these exact names):
- GET /api/queue-items/held → { items: [{ id, heldReason, accountId, providerId,
  commandType, symbol, originalEntry, currentPrice, driftPct, droppedLifecycleCount,
  droppedLifecycle: [commandType], createdAt }] }
- POST /api/queue-items/:id/requeue body { mode: "market" | "original" }
- POST /api/queue-items/:id/dismiss
- DELETE /api/account-slots/:id
- POST /api/trades/:id/resolve body { action: "close_from_history" | "readopt" | "archive" }
- Settings alerting fields: alertBotToken, alertChatId, and boolean toggles
  alertOnGuardianPause, alertOnEaOffline, alertOnExecFailed, alertOnHeld, alertOnTelegramStall.
- POST /api/admin/alert-test → sends a test message via configured bot; 400 if unconfigured.
- POST /api/admin/backup → { filename }; GET /api/admin/backups → { backups: [filename] }.

If budget runs short, stop cleanly at the last green gate; Phase A (shipped) and Stream B
(UI) carry the most user-visible value.
